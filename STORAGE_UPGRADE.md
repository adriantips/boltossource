# Storage startup and failure handling

This continuation addresses Phase 0/1 data-loss paths discovered while auditing
`fs_persist_init()`. It does not declare the OS daily-drivable.

## Shipped behavior

### Selecting and initialising a disk

1. Prefer a boot disk with one valid BoltFS MBR partition.
2. Otherwise prefer existing BoltFS on a data disk, ordered NVMe, SSD, HDD.
   Recognisable legacy raw images remain supported.
3. Only then consider wholly zero-filled, writable, non-boot scratch disks of
   2–64 MiB. Read every sector and reject any nonzero byte or read failure.
   This preserves first-boot setup for the images generated by `build.sh` while
   bounding the time spent scanning during startup.
4. Other disks require the installer. An empty first sector, unknown filesystem,
   or failed mount is never enough evidence to format a disk.

Partition selection rejects out-of-bounds and overlapping MBR entries, multiple
BoltFS partitions and protective/hybrid GPT tables. Sector I/O uses subtraction
for bounds checks, so an overflowing LBA cannot wrap around the device limit.
The installer detaches the actual mounted disk, rather than rerunning selection.

Automatic FAT32 setup applies the same complete-empty-disk check and excludes
BoltFS's attached disk. Recovery never initialises disks and rejects FAT32 writes,
directory creation and formatting.

### Loading an image

Superblocks must describe a slot within the attached partition, with the expected
geometry and a possible record count. Validate lengths before allocation and
checksum traversal, including legacy v1 image lengths.

The loader builds a separate tree. Only after the entire blob succeeds does it
replace the seed tree. Every failure releases the partial tree and its index.
`fsck` uses the same record parser, checking the root, parent ordering and types,
file lengths, node types, terminated names, duplicate names, path components,
depth/path limits and exact consumption of the blob.

A corrupt copy can fall back to the mirror. An allocation failure stops loading
instead of treating a potentially valid newer generation as corrupt and choosing
an older one. If nothing loads, keep the original disk read-only and run the seed
tree in RAM. `fsck` can diagnose the attached image, but `fsck -r`, `sync` and
autosave cannot overwrite it with the seed tree.

Legacy v1 migration writes the new image into slot 1 before replacing its old
superblock. If the legacy blob extends into that slot, keep it read-only; it
needs export to another disk rather than an overlapping migration.

### Commit failures

The existing protocol writes the inactive blob, flushes it, writes and flushes
the primary superblock, then writes and flushes the mirror. All six operations
are checked. Any I/O failure protects the attachment read-only until reboot.
This is necessary because a failed flush may still have persisted the primary:
retrying with the previous in-memory slot number could overwrite live data.

Allocation failure before I/O reports that the commit was not written. It can be
retried with `sync` after memory is available. Export also checks its final flush.

## Using a protected system

- `diskinfo` distinguishes persistent writes from changes confined to RAM.
- File Explorer's status bar warns when storage is protected or volatile;
  System Info labels protected storage `Read-only (RAM)`.
- `fsck` reports image problems without writing; `fsck -r` is refused on a
  protected attachment.
- When a saved image cannot load, the displayed seed files are temporary. Keep
  the original disk for recovery. Do not install over it to regain access.
- After a commit I/O failure, save important live changes elsewhere before
  rebooting; reboot only resolves which completed generation is durable.
- Use the boot menu's recovery entry to inspect a disk without autosave. Changes
  to the in-memory BoltFS tree in this mode are deliberately not persisted.

## Verification

`python test/t_storage.py` runs both layers:

- `test/host/storage.c` compiles the actual block layer and BoltFS with a failing
  allocator and a simulated volatile disk cache. It injects every allocation
  failure in a load and every write/flush failure in a commit, including uncertain
  completion. It discards unflushed writes to model power loss and checks that a
  complete old or new image remains. It also checks malformed records, fsck
  agreement, bounds, read failures, partition selection and legacy migration.
- QEMU boots with private writable disk images, then compares SHA-256 hashes of
  the complete protected disks. Cases cover foreign MBR data, a protective GPT
  disk over AHCI, data at the end of a disk with an empty first sector, a corrupt
  but checksum-valid BoltFS image, mirror fallback, an existing HDD beside empty
  NVMe, fresh scratch initialisation and recovery with attached SATA storage.

Use `python test/t_storage.py --host-only` for the injected-failure tests without
QEMU; set `BOLTOS_HOST_CC` if the host compiler is not discoverable. The normal
`test/run_all.py` discovery includes this test. Existing persistence, installer,
boot and shell tests remain regression checks for the shared storage paths.

## Remaining work

- FAT32 still ignores some write/flush failures and lacks protection against a
  torn directory-sector update. Safer overwrite ordering is not full crash safety.
- Whole-tree autosave can run out of heap or slot capacity; mutations currently
  remain in RAM when the save fails, and not every caller propagates that failure.
- The kernel heap and other subsystems need a broader allocation-failure audit.
- Real hardware power-cut testing, ambiguous selection across multiple complete
  installations, GPT installation and resizing existing BoltFS slots remain open.
- Mirrored superblocks protect commit interruption, not independent corruption
  of both copies or a device that does not honor cache-flush commands.
